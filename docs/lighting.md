# Mythos и освещение KOJIMA

Программная часть работает через **mock-драйвер**. Статусы и переходы — симуляция;
они не подтверждают обнаружение, подключение или управление реальной лампой.
Cloud-драйвер добавлен как явно включаемый транспорт; на игровом сайте он ещё
не включён. Подтверждены авторизация, чтение выбранной лампы и точное
соответствие Blue 55% между LAN и Cloud. Физические облачные переходы
и безопасный выход из RGB ещё требуют проверки.
Отдельными диагностическими утилитами получен ключ и подтверждено чтение лампы
по LAN (H1); облачная карта параметров получена (H2 частично), три белых профиля
сняты из Smart Life и воспроизведены по LAN с проверкой значений и визуальным
подтверждением пользователя (H3 завершён для статических белых профилей).
H2 и этапы H4–H7 ещё не завершены.

Ниже сохранены требования, протоколы проверок и ограничения каждого этапа.

## Запуск симуляции

После установки штатных зависимостей проекта и настройки локальной `.env`:

Для исполнителя освещения с SQLite требуется **PHP 8.4+**: используемая версия
Laravel применяет режим транзакций SQLite `IMMEDIATE` на этом runtime. Требование
PHP 8.3 в `composer.json` остаётся общей нижней границей приложения, но его
недостаточно для этого режима исполнителя.

```bash
php artisan migrate
npm run build
```

В отдельном терминале, с той же `.env` и БД, запустить исполнитель:

```bash
php artisan lighting:work
```

Для локальной проверки с Mac и Android-планшета запустить приложение:

```bash
php artisan serve --host=0.0.0.0 --port=8787 --no-reload
```

На Mac открыть `http://127.0.0.1:8787`, на планшете в той же сети —
`http://<LAN-IP-Mac>:8787`. Адрес Wi-Fi-интерфейса Mac можно узнать командой
`ipconfig getifaddr en0` (при другом интерфейсе подставить его имя).
Используются локальная БД и её учётная запись. Mac должен оставаться включённым
и доступным в сети. Звук воспроизводит браузер планшета, а исполнение света
выполняется на Mac. Пока драйвер `mock`, физическая лампа не управляется.

Исполнитель должен продолжать работать
во время демонстрации: HTTP только принимает намерение, переход исполняется
отдельным процессом. `queue:work` и `QUEUE_CONNECTION=sync` не заменяют
`lighting:work`.

Настройки находятся в `config/lighting.php`; значения по умолчанию позволяют
запустить mock без реквизитов лампы:

| Переменная `.env` | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `LIGHTING_DRIVER` | `mock` | Симуляция; `cloud` включается после аппаратной проверки |
| `LIGHTING_WHITE_FADE_MS` | `4000` | Общая длительность белого перехода, мс |
| `LIGHTING_WHITE_FADE_DOWN_MS` | Значение `LIGHTING_WHITE_FADE_MS` | Необязательное отдельное время затемнения |
| `LIGHTING_WHITE_FADE_UP_MS` | Значение `LIGHTING_WHITE_FADE_MS` | Необязательное отдельное время восстановления белого |
| `LIGHTING_SCENE_FADE_OUT_MS` | `2000` | Гашение тестовой сцены |
| `LIGHTING_DARK_HOLD_MS` | `150` | Минимальное удержание темноты |
| `LIGHTING_CURVE` | `smoothstep` | Кривая перехода; также поддерживается `linear` |
| `LIGHTING_TICK_MS` | `100` | Интервал шага симуляции, не частота команд лампе |
| `LIGHTING_CONTROL_LEASE_MS` | `43200000` | Срок эпохи управления: 12 часов |
| `LIGHTING_MOCK_DELAY_MS` | `0` | Тестовая задержка драйвера |
| `LIGHTING_MOCK_FAILURE` | пусто | Тестовая ошибка: `offline` или `transport_timeout` |

После изменения `.env` перезапустить исполнитель; при включённом config cache
обновить его штатным способом. Название другого драйвера в `.env` не создаёт
подключение к лампе. Для обычной работы симуляции оставить delay равным нулю,
failure — пустым.

Для белых переходов базовое значение — **4 секунды**:
`LIGHTING_WHITE_FADE_MS=4000`. Длительность задаётся в миллисекундах.
Если явно заданы `LIGHTING_WHITE_FADE_DOWN_MS` или
`LIGHTING_WHITE_FADE_UP_MS`, соответствующее направление использует отдельное
значение; прежние явные настройки имеют приоритет над общей длительностью.
Пользователь изменил текущую локальную настройку на
`LIGHTING_WHITE_FADE_UP_MS=8000`: усиление разрешается в **8 секунд**,
затемнение остаётся **4000 мс** через общую настройку. Восьмисекундный вариант
ещё не проверен на лампе; описанная ниже успешная аппаратная проба использовала
прежние 20000 мс.

`lighting:work --once` исполняет один шаг, `lighting:work --ticks=20` — ограниченную
серию шагов для диагностики; для UI нужен непрерывный процесс. Рабочий интервал
ограничен 50–1000 мс, тестовая задержка драйвера — 2000 мс. Исполнитель использует
локальный `flock` вокруг отправки: поддерживается один хост исполнителя. Для
нескольких хостов или будущего bridge потребуется отдельное распределённое
ограждение отправителя. В SQLite принятие намерения сериализуется реальной
операцией записи; чтение состояния и обращение к драйверу не держат транзакцию
на протяжении перехода. Состояние и тёмный барьер сохраняются в БД, журнал и
квитанции идемпотентности ограничены 256 записями.

Для совместной работы исполнителя, database cache и database sessions SQLite
настроен с `busy_timeout=5000` и `transaction_mode=IMMEDIATE`; текущий режим журнала
не меняется. Это позволяет кратким транзакциям получить право записи до чтения
счётчиков rate limiter и устраняет конфликт последующего повышения блокировки.
После изменения конфигурации перезапустить долгоживущие PHP-процессы.

Срок эпохи не продлевается чтением статуса или новыми намерениями. После потери
эпохи новое явное игровое действие может получить управление снова; logout
отзывает его. Закрытие вкладки не равно logout: уже принятое сервером намерение может
завершиться в пределах действующей эпохи. Статус отдаёт последние 20 событий;
при проверке длинных переходов собирать события по `id` между опросами.

По уточнению пользователя ручная панель **Link lighting / Take control / Normal
light** убрана. Нажать **Mythos**: музыка и навигация на `/mythos` запускаются
из этого жеста, а клиент при необходимости получает управление и отправляет
цель тёплого белого 1% / 0%. То же получение управления используется для других
явных игровых действий, которым нужна световая цель. Ожидание ответа света
не задерживает аудио или навигацию. Пока получение управления выполняется,
сохраняется только последняя выбранная цель. Можно выбирать цвет ещё во время
затемнения: после темноты применяется последний выбор. Без выбора цвета
симуляция остаётся в темноте. Цветовые кнопки не управляют аудио.

Прямое открытие `/mythos` и reload не запускают музыку или световую команду.
Для нового входа используется кнопка Mythos в шапке.
На прямом `/mythos` карточки неактивны до нового входа кнопкой Mythos. Mount,
опрос статуса, reload и история не получают управление. Выход из Mythos при
навигации может отправить обычный профиль только с существующей эпохой либо
заменить цель уже ожидающего игрового действия. Неудачное получение или потеря
управления не запускают новое получение сами. Новое игровое действие в другой
вкладке может отозвать старую эпоху; после reload управление не восстанавливается
из сохранённых данных браузера. Logout сразу делает ожидающие действия
неактуальными, включая поздний ответ получения управления.
После нового входа загрузка авторизованного layout выполняет только чтение;
новое явное игровое действие снова может получить управление.

## Перенос на другую площадку и Smart Life

Актуальное решение пользователя: планшет Android, отдельное приложение не
разрабатываем. Проверяем интеграцию существующего сайта через Tuya Cloud с
сервером theyellowsign.ru; если этот путь не подходит, допустим работающий Mac
как локальный исполнитель команд того же сайта. Работа только с планшетом —
цель интеграции, а не уже достигнутое состояние. Новый код приложения попадает
на сервер только через commit/push ветки `feature/kojima-mythos-lighting` и
переключение серверной рабочей копии на эту ветку; `main` остаётся стабильным.
Секреты и приватные калибровки в Git не помещаются.

Mac сейчас запускает локальные диагностические утилиты для лампы. Пример запуска
EH_app на Mac выше — только вариант локальной проверки, а не требование к
размещению сайта во время игры. Пользователь использует сайт через интернет и
имеет серверы в Стокгольме и Москве; постоянный работающий Mac для финальной
схемы нежелателен. Cloud-драйвер реализован, но ещё не включён на игровом сайте.
Удалённый сервер не получает LAN-доступ к лампе только от наличия её приватного
IP и ключа. Для выбранной схемы без Mac проверяются команды через Tuya Cloud.
Обычный сайт в браузере не реализует прямое соединение Tuya TCP.

Tuya Cloud позволяет серверу отправлять команды устройству; стандарт освещения
содержит `scene_data_v2` и `control_data`.
[Tuya: команды](https://developer.tuya.com/en/docs/cloud/e2512fb901?id=Kag2yag3tiqn5),
[Tuya: стандарт освещения](https://developer.tuya.com/en/docs/iot/dj?id=K9i5ql3v98hn3).
Доступ проекта к API и соответствие Blue Cloud JSON исходному LAN payload
подтверждены. Остаются физическая проверка всех переходов и ограничения
действующего пробного доступа Tuya. Текущий плавный белый подъём состоит из серии
DP 28, а не одной команды «переход за 8 секунд»; отправка этой серии через облако
может нарушить равномерность. Точная плавность через Cloud пока не подтверждена.

Имя сети и пароль Wi-Fi лампы задаются при подключении через Smart Life,
а не в `.env` EH_app. Для новой сети понадобится настройка подключения лампы;
для неё используется Wi-Fi 2,4 ГГц.
[Tuya: подключение Wi-Fi-устройства](https://developer.tuya.com/en/docs/iot/user-manual-for-tuya-smart-v3177?id=K9obrofrfk4sk).
Локальные IP, ID, версия протокола и `local_key` хранятся в приватной конфигурации.
После смены сети нужно сверить новый IP с той же лампой. Удаление и повторное
добавление устройства меняют ключ, поэтому тогда требуется получить новый.
[TinyTuya: устранение неполадок](https://github.com/jasonacox/tinytuya#troubleshooting).

Собственная переносная точка доступа 2,4 ГГц может сохранить знакомую лампе сеть
при выездах. Она не заменяет исполнитель и сама по себе не делает сайт автономным.
Полная работа без интернета потребовала бы отдельного локального размещения или
офлайн-реализации сайта и музыки; такого режима сейчас нет. Текущий сайт на
удалённом сервере требует интернета независимо от LAN-доступа к лампе.

Smart Life не требуется держать открытым для прямых команд TinyTuya. Его лучше
закрывать на время LAN-проверки: TinyTuya предупреждает о возможной конкуренции
за единственное TCP-соединение.
[TinyTuya: устранение неполадок](https://github.com/jasonacox/tinytuya#troubleshooting).
Это не доказанная причина прошлых обрывов нашей лампы. После подтверждённого
полного закрытия Smart Life удалось прочитать и сохранить Yellow по LAN без
изменения света. Одно успешное чтение не доказывает длительную устойчивость;
её ещё предстоит проверить отдельно.

## Профили и принятая политика

| Выбор | Белая яркость | Тепло-холодный баланс |
| --- | ---: | ---: |
| Action / Muted Action | 100% | 33% |
| Encounters | 90% | 20% |
| Тёмная точка | 1% | 0%, RGB погашен |

Проценты описывают пользовательские цели, а не сырые значения лампы. Тёмная
точка не означает выключение питания. Любой выход из цветной сцены проходит
через неё, даже если во время перехода пользователь несколько раз сменил цель.

Стартовые длительности из плана: белое затемнение и восстановление — по 5000 мс,
гашение сцены — 2000 мс, удержание достигнутой темноты — 150 мс. Фильтр случайного
повтора одной команды — 250 мс; другой выбор принимается сразу. Эти значения
предназначены для симуляции и требуют физической калибровки.

- Повтор уже выбранного цвета не перезапускает сцену. Актуальное оформление
  карточек — три фоновых изображения пользователя, без видимых слов Green,
  Yellow, Blue и вспомогательного текста. Изображение не задаёт RGB лампы.
- Осмысленный повтор Mythos сохраняет audio toggle-stop и текущий световой
  контекст. Пауза, громкость, автопродолжение трека и добавление blob света не меняют.
- Combat, Epic Combat и Other при выходе из Мифов возвращают последний обычный
  профиль; резервный профиль — Action. Вне Мифов они не задают новый профиль.
- Явный Encounters выбирает 90% / 20% и сохраняет навигационное аудиоповедение.
- Уход со страницы Mythos через Home / Back / Other завершает контекст Мифов.
  Action завершает его и при остающейся открытой странице; старые цветовые события
  больше не действуют.
- Для возврата к обычному профилю используется игровой выбор Action; отдельной
  кнопки Normal light нет. После цвета сохраняется обязательная тёмная точка.
- Logout отменяет дальнейшее исполнение; сам выход не включает яркий белый свет
  и не выключает лампу. Техническое отключение управления остаётся в API.

Актуальные требования к странице: заголовок **Mythos**; пункт Mythos в шапке
использует `›` так же, как Encounters и Other. Green, Yellow и Blue остаются
внутренними именами выбора; видимые подписи цветов на карточках не нужны.
Карточки приведены к общей `ButtonGrid` шириной до `48rem` и размеру
`ui-main-btn`, как на Side Boards / Quest / Disaster. Сборка после этого изменения
прошла. В браузере размеры и координаты всех трёх карточек совпали с Side Boards,
Quest и Disaster на desktop 1440×900 и iPad 1024×768. На телефоне 600×390
карточки совпадают с однострочными Side Boards/Disaster; существующий перенос
Dream-Quest на две строки увеличивает высоту всей строки Quest. Невидимая
строка в Mythos сохраняет высоту обычной кнопки без видимой подписи; минимальная
область нажатия — 44 px. Ошибок JavaScript в проверке не было.
Белая кайма исходных PNG исключена отдельными SVG-масками по форме рамок;
исходные изображения и размеры кнопок сохранены. Выбранная карточка отмечается
цветным свечением, клавиатурный фокус — цветным контуром, без белой окантовки.

Для Yellow пользователь выбрал отдельный DIY-пресет с точным именем **Yellow**
и режимом «Дыхание». Это актуальный выбор вместо исходных вариантов
«Расплата: Начало» / «Расплата: Текст». Точный пресет Yellow со скоростью 40
считан по LAN и сохранён в приватной коллекции; воспроизведение ещё предстоит
проверить. Не настроенный физический alias должен возвращать
`preset_not_configured`. Игровой драйвер пока использует mock.

## Контракт и границы исполнения

Защищённые маршруты приложения:

| Запрос | Назначение |
| --- | --- |
| `GET /lighting/status` | Только безопасный статус, без побочных действий |
| `POST /lighting/control` | Явное получение или отключение управления |
| `POST /lighting/intents` | Полная логическая цель с `intentId`, `clientSeq`, `controlEpoch` |

HTTP 202 означает принятие, а не завершение перехода. Повтор того же намерения
не создаёт второй переход. Старая эпоха или последовательность не могут заменить
новую цель. Рабочий процесс исполняет актуальное желаемое состояние, а не историю
цветов в FIFO. Тёмный барьер сохраняется при смене цели и перезапуске исполнителя.

Браузер передаёт только профили и цвета. API не принимает адрес устройства,
DP, команды оболочки или raw-payload. Наблюдения mock имеют `quality=simulated`;
ошибка света не блокирует аудио или навигацию. Диагностический статус доступен
через API.

Реальный локальный драйвер должен исполняться в сети, доступной лампе. Размещение
Laravel на внешнем сервере само по себе такого доступа не создаёт. Выбор между
локальным посредником и подтверждённым облачным API будет сделан после H1.

## Проверки

```bash
php artisan test
npm run test:unit
npm run build
```

PHP-тесты запускать только с отдельной тестовой БД (штатный `phpunit.xml` использует
SQLite `:memory:`). Миграция приложения добавляет таблицы освещения; `migrate:fresh`
для установки не нужен. Тесты mock проверяют программный порядок, отмену и тёмный
барьер; они не измеряют световой выход, плавность лампы или поведение реального
мобильного браузера.

Текущее игровое устройство — **Android-планшет**, работа над проектом ведётся на
Mac. Основная ручная приёмка проводится на этом планшете в **Android Chrome**
и, если используется установка на главный экран, в PWA: музыка переживает
Inertia-навигацию, tap/hold не дублируются, кнопки и статус помещаются в экран,
клавиатурный фокус видим, пауза и громкость работают как раньше. На реальном
планшете отдельно проверить слышимый звук, первый запуск музыки после входа,
возврат из фонового режима и ориентацию экрана. Проверка iPad Safari остаётся
дополнительной проверкой совместимости. С лампой повторяется применимая часть
U/R/E-матрицы после H1–H7.

## Аппаратная диагностика H0–H7

В ходе разработки mock сеть и физическая лампа не проверялись. Для отдельного
аппаратного этапа добавлен `scripts/lighting/discover.py`: он получает объявления
Tuya в LAN, без опроса состояния, перебора IP и команд изменения света.
Диагностическое окружение изолировано от PHP/JS-зависимостей:

```bash
python3 -m venv storage/app/private/lighting/venv
storage/app/private/lighting/venv/bin/python -m pip install --only-binary=:all: -r scripts/lighting/requirements.txt
storage/app/private/lighting/venv/bin/python scripts/lighting/discover.py --seconds 15
```

Если широковещательное обнаружение ничего не находит, но локальный IP известен
из роутера или ARP, можно отправить запрос обнаружения только этому адресу:

```bash
storage/app/private/lighting/venv/bin/python scripts/lighting/discover.py --ip <LAN-IP-лампы> --seconds 10
```

Этот режим отправляет `REQ_DEVINFO` по UDP, принимает объявления и не читает DPS
и не меняет свет. После перепривязки адрес, ID и ключ нужно проверить заново.

Полные идентификаторы сохраняются в исключённый из Git
`storage/app/private/lighting/discovery.json` с правами доступа только владельцу.
В терминале показываются адрес, версия и последние шесть символов ID.
Найденный адрес нужно сопоставить с конкретной лампой в текущем приложении; обнаружение
не означает наличия `local_key` или успешного управления.

### H1 — обнаружить устройство и безопасно прочитать состояние

TinyTuya требует адрес, `device_id`, фактическую версию протокола и `local_key`
для локального управления. Для обнаружения используются UDP 6666/6667/7000,
для соединения — TCP 6668; их доступность проверяют внутри своей сети, без открытия
в интернет. Обнаружение не даёт локальный ключ.
[TinyTuya: подготовка устройства](https://github.com/jasonacox/tinytuya#tuya-device-preparation).

После переноса сначала проверить ручное управление в Smart Life, затем связать
его аккаунт через **Devices → Link App Account → Add App Account** в проекте Tuya.
QR сканируется из Smart Life; после подтверждения аккаунт и лампа должны появиться
в проекте. Повторить обнаружение командой выше и сверить актуальные ID/IP/версию.

В собственном терминале запустить из корня проекта:

```bash
storage/app/private/lighting/venv/bin/python scripts/lighting/configure.py
storage/app/private/lighting/venv/bin/python scripts/lighting/read_state.py
```

`configure.py` запросит актуальные реквизиты лампы, регион проекта (`eu-w` для
Western Europe, `eu` для Central Europe) и скрытым вводом Access ID/Secret.
Получает данные только выбранного устройства. Облачные реквизиты не сохраняются;
локальный ключ записывается в исключённый из Git `device.json` с правами `0600`.
Ключи не вставлять в чат или аргументы командной строки.

`read_state.py` использует только `Device.status()` с указанной версией,
ограниченными временем и повторами; автоматический перебор DP отключён.
Сырой ответ сохраняется приватно, в терминале видны только номера и типы DPS
либо код ошибки. Версия 3.2 отклоняется: TinyTuya автоматически перебирает DP
при её установке. Закрыть панель мобильного приложения, если она конкурирует
за TCP-соединение. Эти утилиты не меняют свет и не являются драйвером EH_app.
[TinyTuya: соединение](https://github.com/jasonacox/tinytuya/blob/master/API.md#xenondevice-base-class),
[ограничения LAN](https://github.com/jasonacox/tinytuya#troubleshooting).

**Критерий:** прочитано состояние именно этой лампы. Отсутствие обнаружения ещё
не устанавливает причину: проверить сеть, изоляцию клиентов, версию и транспорт.

### H2 — установить карту параметров

Зафиксировать поддерживаемые режимы, DP/schema, диапазоны, единицы, возможности
остановки перехода и смысл статуса: текущее значение или только заданная цель.
Не переносить DP 20–25, версию 3.3 или тип B с похожей лампы. Не включать поддержку
`safeSceneExit` до физической проверки H6.

**Подтверждено для этой лампы:** запрос
`GET /v1.1/devices/{device_id}/specifications` вернул успешный ответ; полная схема
сохранена приватно. Это результат запроса конкретного устройства, а не выбор
типовой карты. Назначение API описано в
[Tuya: Get Device Specification Attribute](https://developer.tuya.com/en/docs/archived-documents/f2c0abfbbd?id=Kb26d4cf4wnrd).

| DP | Код | Тип и диапазон облачной схемы |
| --- | --- | --- |
| 20 | `switch_led` | Boolean |
| 21 | `work_mode` | Enum: `white`, `colour`, `scene`, `music` |
| 22 | `bright_value_v2` | Integer: 10–1000, шаг 1, scale 0 |
| 23 | `temp_value_v2` | Integer: 0–1000 |
| 24 | `colour_data_v2` | JSON HSV: h 0–360, s/v 0–1000 |
| 25 | `scene_data_v2` | JSON: scene_num 1–8, типы элементов `static`, `jump`, `gradient` |
| 26 | `countdown_1` | Integer: 0–86400 секунд |
| 27 | `music_data` | JSON; s/v 0–255 |
| 28 | `control_data` | JSON; s/v 0–255 |
| 34 | `do_not_disturb` | Boolean |

Прочитанный LAN-статус содержит восемь DP: 20–26 и 34. DP 24 и 25 приходят
строками; их LAN-кодировка и импорт сцен пока не подтверждены. Диапазоны s/v
для DP 27/28 отличаются от DP 24 — использовать их как взаимозаменяемые нельзя.
Полученная карта не подтверждает текущий физический свет: статус может отражать
заданную цель. Семантика переходов, кодировки, калибровка и безопасный выход из
сцены ещё не проверены; H2 остаётся частично выполненным.

Для дальнейшего разбора DP 25 стандартный LAN-формат описан как два
hex-символа ID сцены и блоки по 26 hex-символов на точку. Текущая длина 28
совместима с одной точкой, но не доказывает содержание пользовательских сцен.

длительности в стандартном формате нет. Нельзя считать `gradient` переходом
заранее заданной длительности. Постоянные DP и конфигурация сцены также не
подтверждают мгновенную яркость текущей фазы «Дыхания».
[Tuya: Function Definition](https://developer.tuya.com/en/docs/iot/product-function-definition?id=K9s9rhj576ypf),
[Lighting SDK](https://github.com/tuya/tuya-lighting-ios-sdk/blob/main/README.md),
[Panel DP Description](https://developer.tuya.com/en/docs/iot/product-panel-dp-interactive-description?id=K9s9rhiowe806).

Пользователь последовательно установил и подтвердил три профиля в Smart Life;

| --- | --- | --- | --- |

Это измеренные соответствия показаний приложения и прочитанного состояния;

Выполнено программное воспроизведение `encounters` → `action` → `dark` с паузами
по 4 секунды плюс время выполнения инструментов. Для каждого профиля отправлен
один CONTROL с DP 20–23; после закрытия соединения отдельное новое чтение
подтвердило точное совпадение значений (`ok=true`, `readback_matched=true`).
Итоговый прочитанный режим — включённый белый свет, DP 22 = 10, DP 23 = 0.

Предварительное чтение до включения Blue вернуло 8 DPS и белый режим `on`,

Следующий шаг — проверить ограниченные Cloud-команды на сервере и сопоставить
результаты с фактическим светом и свежими отчётами устройства.
Пример из корня проекта; `EXACT_DEVICE_ID` — точный ID своей лампы,
`STATUS_SNAPSHOT.json` — имя нового приватного файла, созданного `read_state.py`:

```bash

storage/app/private/lighting/venv/bin/python scripts/lighting/scene_profile.py capture --expect-device-id EXACT_DEVICE_ID --alias yellow --snapshot STATUS_SNAPSHOT.json --user-confirmed
storage/app/private/lighting/venv/bin/python scripts/lighting/scene_profile.py list --expect-device-id EXACT_DEVICE_ID
storage/app/private/lighting/venv/bin/python scripts/lighting/scene_profile.py validate --expect-device-id EXACT_DEVICE_ID
```

`scene_profile.py` работает только с локальными файлами. Захват требует
совпадающего ID, протокола 3.5, `on`, режима `scene` и полного DP 25; все элементы
проверяются по сохранённой схеме устройства. В приватном `scene-presets.json`
сохраняются точная строка DP 25 с исходным регистром, SHA-256, alias, имя снимка
и время захвата. Другие данные для уже занятого alias по умолчанию отклоняются;
повтор того же payload допустим. Явная замена использует
`capture --replace-sha256 PREVIOUS_SHA256` вместе с `--user-confirmed`: проверяется
контрольная сумма текущего пресета, вся прежняя коллекция сохраняется отдельным
приватным backup, затем новый payload записывается атомарно с
`replay_verified=false`. При несовпадении ожидаемой суммы или ошибке сохранения
backup исходная коллекция не меняется. `validate --snapshot STATUS_SNAPSHOT.json` проверяет
отдельный снимок, без этой опции — сохранённую коллекцию.

Автоматической проверки возраста снимка нет: новый снимок после активации и
подтверждение пользователем обязательны для правильного сопоставления имени.
Один `status()` не экспортирует всю библиотеку DIY-сцен. До захвата Blue проверка
`list` вернула пустую коллекцию, а белый снимок был отклонён с
`snapshot_must_be_on_and_scene`. LAN-воспроизведения в этом инструменте нет;
`replay_verified` при первом захвате остаётся `false`. H4 ещё не завершён,
игровой драйвер остаётся mock.

Для отдельной проверки воспроизведения подготовлен и проверен автономными
тестами `scene_replay_probe.py`; **на лампе он ещё не запускался**:

```bash

```

Он допускает запуск только из уже подтверждённого калиброванного Dark 10/0,

повторной записи и автоматического выхода или отката при отмене нет: DIY-сцена

### H5 — проверить белые переходы

Добавлена отдельная проверка встроенного белого перехода через DP 28 одной
командой (`scripts/lighting/native_white_probe.py`). Формат не содержит поля
длительности; HSV обнулён, белые значения взяты из подтверждённой калибровки.
Диагностические Python-инструменты проходят 115 автономных тестов; PHP-обвязка
пробы — 7 тестов с 25 assertions, Pint проходит.

Первая команда dark → action (10/0 → 1000/332) отправлена без ожидания ACK.
Отдельное чтение вернуло сохранённые 10/0; DP 28 может менять текущий световой
выход, не обновляя эти значения. Поэтому чтение не доказывает ни отсутствие
изменения, ни завершение перехода. Пользователь визуально подтвердил, что
переход был плавным, но занял **меньше секунды**. Этого недостаточно для
запрошенных 3–5 секунд; H5 не пройден.

Для управляемой длительности добавлена Artisan-команда `lighting:probe-white`, которая
получает итоговые длительности из `config/lighting.php`, включая общую
`LIGHTING_WHITE_FADE_MS=4000` и отдельные UP/DOWN-настройки. В первых пробах
оба направления разрешались в 4000 мс; затем UP был 20000 мс для успешной
аппаратной пробы. Текущий отдельный UP равен 8000 мс и ещё не проверен на лампе,
DOWN остаётся 4000 мс.
Проба поддерживает только полный переход между `dark` и `action`. Подставить
точный идентификатор своей лампы вместо `EXACT_DEVICE_ID`. В этих примерах
используется режим по умолчанию `--native-mode=gradient`:

```bash
php artisan lighting:probe-white dark action --expect-device-id=EXACT_DEVICE_ID
php artisan lighting:probe-white action dark --expect-device-id=EXACT_DEVICE_ID
```

Первое направление использует итоговое значение UP, обратное — DOWN. Без
`--require-source` команда сначала явно устанавливает исходный статический
профиль и выдерживает 1 секунду.
Утилита
`scripts/lighting/timed_white_probe.py` распределяет промежуточные значения
белого света по заданному времени и отправляет DP 28 с `gradient` каждые 100 мс.
После последней цели предусмотрена дополнительная пауза 1 секунда, затем
сохранение конечного статического профиля. Подготовительная и конечная паузы
не входят в заданное время отправки промежуточных целей (в первых пробах —
4 секунды).

Аппаратная проба dark → action с общей настройкой 4000 мс выполнена:
40 промежуточных целей отправлены за 4001,68 мс; максимальная длительность
отправки — 0,417 мс, максимальное отставание от расписания — 5,05 мс.
После сохранения конечного профиля отдельное чтение подтвердило 1000/332.
Это подтверждает расписание отправки и сохранённую цель, но не физическую
обработку каждого кадра лампой. Пользователь увидел **3–4 заметных быстрых скачка
примерно раз в секунду** вместо непрерывного плавного перехода. Проверка H5
не прошла критерий плавности; требуется исправление, причина пока не установлена.

Затем подготовлен контролируемый эксперимент с `--native-mode=direct`:
сохраняются 4 секунды, шаг 100 мс и кривая `smoothstep`, меняется только флаг
DP 28 с `1` (`gradient`) на `0` (`direct`). Цель — сравнить влияние
встроенного градиента. Первая попытка остановлена на предварительном чтении с
`device_error_905`: отправлено **0 управляющих команд**. По адресу 192.168.0.100
также не ответили TCP 6668, ping и адресный UDP discovery; Mac остаётся в той же
подсети. Повтор отложен до восстановления доступности лампы.

Перед повторной пробой `direct` пользователь открыл Smart Life: сначала увидел
«0/1» (порядок сохранён как в его сообщении), затем показания быстро сменились
на 100/33; фактическая видимая яркость не изменилась. Это историческое наблюдение
согласуется с обновлением устаревших показаний интерфейса, но не доказывает
отправку новой команды или наличие ожидающей сетевой очереди.

чтение вернуло исходные 10/0; отдельное чтение примерно через 22 секунды тоже

пробы не прошли визуальную приёмку плавности, H5 остаётся незавершённым.

Временный световой выход от DP 28 и сохранённые DP 20–23 следует учитывать
отдельно: ни старые показания интерфейса, ни расписание отправки не подтверждают
физическую обработку каждого кадра или сохранение конечной цели. Обработка
ответов соединения и фиксация конечного профиля затем доработаны и проверены
следующей аппаратной пробой. Причина скачков пока не установлена.

Добавлен вариант `--receive-responses`: чтение аутентифицированных ответов
между командами, сохранение частичных кадров, проверка конечных DP20–23

не подтверждает состояние; повторов управляющих команд нет.

Аппаратная проба `direct --receive-responses` отправила 40 промежуточных целей
за 4005,375 мс и получила 47 ответов. Конечные **1000/332 подтверждены** на
исходном соединении и отдельным чтением. Визуальная плавность этой новой пробы
пока ожидает подтверждения пользователя. ACK приходят пачками примерно раз
в секунду, а не равномерно вместе с отправкой команд.

Отдельная проверка ICMP с интервалом 200 мс показала тот же ритм:
RTT 905 → 701 → 501 → 301 → 96 мс в одной группе ответов; среднее 503 мс,
максимум 915 мс, потерь в 12 пакетах нет. Для шлюза те же 12 пакетов дали
среднее 2,942 мс, максимум 3,429 мс, без потерь.
Периодическая доставка существует и вне протокола управления яркостью.
Энергосбережение Wi-Fi клиента / listen interval — рабочая гипотеза,
точная причина и настройки роутера ещё неизвестны. Пользователь сообщил модель
TP-Link EC225-G5 (AC1300 MU-MIMO); лампа в основной домашней сети 2,4 ГГц,
не в гостевой. [Связанное с моделью руководство TP-Link](https://www.tp-link.com/ca/document/17673/)
описывает Advanced → Wireless → Advanced Settings → 2.4GHz: DTIM, Beacon,
WMM и Airtime Fairness. Реальные значения ещё не прочитаны; пример DTIM=1 в
общем руководстве не доказывает настройку этой провайдерской прошивки.
Роутер не изменялся.
Это основание проверить сетевой режим и встроенный переход в самой лампе,
а не считать увеличение частоты исходящих команд исправлением плавности.

Для отдельной калибровки добавлен диагностический
`scripts/lighting/native_scene_probe.py`: DP25, белая градиентная точка,
HSV 0/0/0, яркость/температура 1000/332, `time=speed=40`.
[Первичный SDK Tuya](https://github.com/tuya/tuya-lighting-ios-sdk/blob/main/README-zh.md)
описывает время в единицах 100 мс; по этому описанию первоначально проверялся
кандидат на 4 с. Однако в
[официальном примере встроенной прошивки Tuya](https://github.com/tuya/tuya-iotos-embeded-sdk-wifi-ble-bk7231n/blob/master/apps/tuya_demo_light_pwm/src/light_app/light_control.c#L1038)
функция `_light_ctrl_data_calculate_scene` для градиента рассчитывает время точки
как `(110 - timeByte) * 100` мс, а время перехода — как половину этого значения.
В этом примере байт 40 означает 7000 мс на точку и 3500 мс на переход.
Это другой контракт времени; принадлежность прошивки нашей лампы этому примеру
не установлена. **`time=speed=40` не является подтверждёнными четырьмя секундами
физического перехода.**
Первая аппаратная проба завершена: отправлены две управляющие записи и три
запроса, получено девять ответов. Сохранённый исходный профиль и сохранённая
сцена подтверждены чтением (`storedSourceConfirmed=true`,
`storedSceneConfirmed=true`); после команды выдержано 20004,245 мс наблюдения
при заданной длительности перехода 4000 мс. Результат `ok=true` подтверждает
эти проверки сохранённого состояния, а не физическое завершение перехода.

Пользователь сообщил: сначала лампа быстро и плавно потемнела менее чем за
секунду (ожидаемая установка исходного профиля), затем так же быстро, менее
чем за секунду, стала яркой одним непрерывным переходом без рывков. О повторе
пользователь не сообщил. Сохранение сцены подтверждено, но **физическая
длительность 4 секунды не достигнута**: однократный четырёхсекундный переход
этой одноточечной сценой не принят, H5 не закрыт. Отсутствие сообщения о повторе
само по себе не закрывает проверку однократности и удержания цели.
Перед следующей пробой выполнено восстановление Action отдельной утилитой
со строгой проверкой сохранённого результата: одна управляющая запись,
подтверждение профиля на соединении отправителя и новое независимое чтение
1000/332. Это подтверждает восстановление сохранённого белого профиля после
диагностики; безопасный визуальный выход из динамического RGB (H6) этим
не проверялся.

Следующий эксперимент выполнен с `--program=anchored` и тремя точками:
исходный `dark` (10/0, `time=speed=10`, mode 2), затем `action` (1000/332,
`time=speed=40`, mode 2), затем та же цель `action` с `time=speed=10`, mode 0.
Отправлены две управляющие записи и три запроса, получено девять ответов;
сохранённый исходный профиль и сохранённая сцена подтверждены чтением.
Наблюдение после команды длилось 30003,604 мс. `ok=true` относится к этим
проверкам сохранённого состояния.

Пользователь подтвердил очень плавное затемнение и плавное усиление белого света.
Затемнение хочется сделать немного медленнее, усиление — примерно вдвое
медленнее. При этом программа продолжала повторяться примерно каждые

Встроенный плавный белый переход визуально подтверждён, но однократность не

Нельзя предполагать остановку по последней точке или считать H5 завершённым.
Для прекращения повторов отправлена одна команда статического Action.

Сохранённый выход из циклической сцены в белый Action подтверждён; активная

длительности переходов или безопасный визуальный выход из динамического RGB.
Опыты с `native_scene_probe.py` выше сохранены как исторические: они могут
оставлять сцену активной. Теперь обычный запуск этой утилиты отказывается от
выполнения **до обращения к лампе**; прежний режим доступен только с явным
`--leave-scene-active`. Библиотечные функции прежней пробы сохранены для
автономных сравнений.

Для дальнейшей диагностики готов `scripts/lighting/native_white_once_probe.py`.
Он начинает только из уже установленного и прочитанного исходного белого
профиля; начальной управляющей записи для сброса профиля нет. Экспериментальная
программа содержит восемь градиентных точек: исходную с байтом времени 100 и
семь одинаковых целевых с байтом 1. Это проверка обратной зависимости времени,
а не установленная формула для этой лампы. Примерно через 9 секунд выполняется
явный выход в конечный статический белый профиль, затем проверяется состояние
и выполняется свежее чтение.

На всю пробу приходится не более двух управляющих записей: сцена и выход.
Отмена проверяет принадлежность активной пробы; при неопределённом результате
выхода допускается только сверка чтением, без повторной отправки команды.
`stoppedConfirmed` и `mayStillLoop` отдельно отражают подтверждение сохранённого
выхода и риск продолжения сцены. Они не заменяют визуальную проверку:
физическая однократность пока не подтверждена.

Обе ограниченные пробы выполнены с байтом времени 1 и выходом через 9000 мс.
**Action → Dark** завершилась сохранённым белым 10/0, затем **Dark → Action** —
белым 1000/332. В каждой пробе отправлены две управляющие записи, получено
восемь ответов; конечные значения подтверждены на соединении отправителя и
новым независимым чтением. Оба отчёта содержат `stoppedConfirmed=true` и
`mayStillLoop=false`. Отправка выхода отстала от расписания на 5,058 мс и
5,082 мс соответственно. Последнее подтверждённое состояние — белый Action.
Повторное чтение примерно через 60 секунд после выхода вновь подтвердило
`true/white/1000/332`: сохранённое состояние не вернулось в режим сцены.

Пользователь оценил затемнение как очень плавное и удачное; его можно немного
замедлить. Усиление света всё ещё слишком быстрое: пользователь хочет сначала
получить переход в несколько раз медленнее, затем при необходимости ускорить.
Длительность пары не принята, H5 остаётся открытым. О новом зацикливании
пользователь не сообщил, но явного визуального подтверждения отсутствия повторов
пока нет; отложенное чтение доказывает сохранённый белый режим.

Для описанной ниже исторической пробы усиления было настроено
`LIGHTING_WHITE_FADE_UP_MS=20000`. Вариант использует DP 28 `gradient` раз в
300 мс и кривую `perceptual`:
прогресс `p^2.2` применяется к обоим белым параметрам, DP 22 и DP 23, чтобы
начало усиления было медленнее. PHP-команда принимает `--tick-ms`, `--curve` и
`--require-source`; проба ограничена 30 секундами и 300 промежуточными целями.

```bash
php artisan lighting:probe-white dark action --expect-device-id=EXACT_DEVICE_ID --tick-ms=300 --curve=perceptual --require-source --receive-responses
```

При новом запуске команда прочитает текущий UP — теперь 8000 мс; это уже другая,
пока не проверенная на лампе длительность.

Перед этой пробой для установки Dark сохраняется уже проверенное плавное
встроенное затемнение. `--require-source` требует точного уже установленного
исходного белого профиля, без его повторного сброса; принимаются ответы лампы,
в конце выполняется одна запись конечного профиля с проверкой чтением.
Ранее наблюдавшаяся доставка пакетами примерно раз в секунду остаётся риском
для плавности: более редкая отправка и новая кривая сами по себе её не
доказывают.

Подготовительное встроенное затемнение выполнено: две управляющие записи,
восемь ответов, белый Dark 10/0 подтверждён на соединении отправителя и новым
чтением; сохранённый выход из сцены подтверждён. Первая PHP-проба усиления
на 20 секунд остановилась на предварительном чтении с `device_error_905`:
`commandsAttempted=0`, `nativeFramesSent=0`. Ни один кадр этого усиления в лампу
не отправлен.

В тот момент отдельное чтение также вернуло 905, лампа не отвечала на ICMP,
а шлюз оставался доступен. Затем связь восстановилась: новое чтение подтвердило
включённый белый Dark 10/0, все четыре ICMP-пакета получили ответы.
Пользователь уточнил, что Mac и телефон подключены к 5 ГГц, лампа — к 2,4 ГГц;
это не препятствует подтверждённому сейчас аутентифицированному LAN-доступу.
Причина временной недоступности не установлена.

Повторная проба усиления с UP=20000 мс завершилась успешно (код выхода 0):
кривая `perceptual`, шаг 300 мс, `require_source=true`, чтение ответов включено
(`--receive-responses`). Отправлены 67 команд:
66 промежуточных кадров DP 28 `gradient` и одна запись конечного профиля;
расписание промежуточных целей заняло 20003,302 мс, получено 70 ответов.
Полное конечное состояние `true/white/1000/332` подтверждено на соединении
отправителя и новым независимым чтением. Сцена и цикл не запускались, процесс
завершён.

Пользователь явно подтвердил этот двадцатисекундный переход как **плавный и
медленный**. Исторический вариант **Dark → Action** принят: расписание 20 секунд, шаг 300 мс,
`perceptual`, DP 28 `gradient`, `--receive-responses`, `--require-source`.
Физическая длительность не измерялась секундомером: 20003,302 мс — измерение
расписания отправителя. Плавность затемнения была принята ранее.
Прерывания, смена цели и другие переходы ещё не прошли полную проверку H5;
игровой драйвер остаётся mock.

Это отдельная диагностическая запись в лампу: она не включает аппаратное
управление из приложения, игровой драйвер остаётся `mock`. После изменения
`.env` при наличии config cache выполнить `php artisan config:clear` либо
штатно пересоздать cache; уже запущенный `lighting:work` перезапустить для
загрузки новых настроек.

Начальная точка здесь — проверенный профиль **1% / 0%** (DP 22 = 10,
DP 23 = 0, лампа включена), а не настоящий нулевой свет или `off`. Переход
именно от 0% ещё не проверен. Предыдущие пробы явно устанавливали исходный
профиль; новая ограниченная проба проверяет уже установленный белый профиль.
Старые DP сцены не подтверждают текущий физический световой выход.

Проверить 100/33 → 1/0 и обратно, затем смену цели на 20%, 50%, 80% перехода.
Не должно быть вспышки на исходной яркости, скачка при прерывании или позднего
возврата старой цели. Откалибровать длительности и способ подтверждения темноты:
сигнал завершения либо проверенная временная модель с запасом.

Подтвердить погашенный RGB в точке 1/0 и отсутствие возобновления старой сцены.
Успешный API-ответ и одновременная отправка параметров не заменяют наблюдение.

В [эталонном коде Tuya](https://github.com/tuya/tuya-iotos-embeded-sdk-wifi-ble-bk7231n/blob/master/apps/tuya_demo_light_pwm/src/light_app/light_control.c)
